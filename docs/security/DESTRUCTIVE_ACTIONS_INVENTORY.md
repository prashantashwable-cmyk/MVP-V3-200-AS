# Destructive Actions Inventory

Generated by `scripts/generate-destructive-actions-inventory.ts` — do not hand-edit.
Re-run after any screen change: `npx tsx scripts/generate-destructive-actions-inventory.ts`.

Regenerated: 2026-09-23

## Method

Live scan of every `src/components/*.tsx` file for a call to a
delete/remove/revoke/deactivate/disable-shaped method or handler function.
Classified into 4 risk tiers by keyword (a file with multiple matches is
filed under its single HIGHEST tier): **irreversible** (delete/revoke/purge),
**financial_security** (refund/payout/discount/credential/permission/role/
password), **important** (deactivate/disable/suspend/cancel/reject),
**reversible** ("remove" alone — usually a re-addable line item or filter, not
permanent data loss). `hasConfirm` is an approximate proxy (any `confirm(`/
`window.confirm(` call anywhere in the same file) — a real per-action check
would need to trace each specific handler, which this pack's own rule against
"pointless confirmation dialogs everywhere" argues against automating blindly.

## Recommendation, by tier

- **irreversible** and **financial_security** — SHOULD confirm before acting.
  These are the tiers where a mistaken tap has a real, hard-to-undo cost.
- **important** — confirm when the action affects someone else's active work
  (e.g. deactivating a user, cancelling a job already in progress); a judgment
  call per screen, not a blanket rule.
- **reversible** — do NOT add a confirmation dialog by default. Per this
  pack's own explicit rule, a dialog on every reversible action trains users to
  click through them without reading, which makes the dialogs on the tiers that
  actually matter LESS effective, not more.

## Manual review findings (why automated detection alone is not enough)

Two real findings from actually reading a sample of the flagged files, kept
here because they show why this report is a starting point for human judgment,
not a list to mechanically "fix" top to bottom:

- **`SecuritySessionManagementScreen`** (`revokeUserSession`/`handleRevokeSession`,
  tier `irreversible`) is flagged as having no `confirm()` — but it already has a
  real, well-built custom confirmation MODAL (`sessionToRevoke` state + a
  "Revoke Device Session?" dialog with Cancel/Confirm buttons), just not a
  literal `confirm(`/`window.confirm(` call. A false positive in this script's
  keyword scan, not a real gap — left unfixed deliberately.
- **`PaymentStageScheduleSetup`**'s `handleDeleteStage` (tier `irreversible` by
  keyword) only removes a stage from an in-memory DRAFT being edited (`setStages`
  React state) — nothing is persisted until a separate, later "Save Draft"
  action. Genuinely reversible in practice (undo by re-adding, or simply not
  saving), despite the "delete" name. Left without a confirmation dialog
  deliberately, per this pack's own rule against pointless ones.

## What Phase 23 fixed vs. reported

This inventory is measured and reported in full. A small, high-confidence
subset of the `irreversible` tier with NO confirm() anywhere in the file was
fixed directly this phase with a native `window.confirm()` — see
`docs/aiec-implementation-log.md`'s Phase 23 entry for exactly which screens
and why those specific ones. Fixing the remaining count at scale, across dozens
of screens this sandbox cannot visually re-verify without a browser, is real,
separate follow-up work — reported honestly here rather than left unmeasured or
claimed done.
