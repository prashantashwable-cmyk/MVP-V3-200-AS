## What this report means

- **server-enforced** — a real Firestore security rule (Phases 04-12,
  `firestore.rules`) governs this entity's collection. A malicious or buggy
  client cannot bypass the check by calling Firestore directly, regardless of
  what the UI shows or hides.
- **client-only** — the only authorization check is `src/lib/authz.ts`'s
  `evaluatePermission()`/`assertPermission()`, called from UI code. This is a
  real, honest UX improvement (a denied action fails loudly with a clear
  reason) but is explicitly **not a security boundary** — anyone who can reach
  the underlying `DbManager` persistence (localStorage today; a future real
  backend if `DbManager` is ever pointed at one) bypasses it entirely. Rule #8
  ("do not rely on UI hiding as authorization") names exactly this risk.

  the same live data `docs/migration/screen-migration-matrix.md` uses — not a
  hand-estimated count.

  found (the hardcoded demo OTP/password login bypasses — see the repo root
  `docs/aiec-implementation-log.md` Phase 23 entry for the fix and its honest
  bundle-text caveat).
- Did NOT: close the client-only gap at scale this phase — that is exactly the
  ongoing screen-migration work Phases 15-18 (and any future continuation of
  that pattern) already do, one real domain/workflow at a time. Marking every
  remaining screen `MIGRATED` in one phase would mean either fabricating the
  migration (forbidden) or rewriting dozens of complex screens blind (this
  sandbox has no browser to verify the result), both explicitly against this
  pack's non-negotiable rules.
