## The real objective

Per this phase's own brief: **the objective is not "101 screens changed." The
objective is: no security-sensitive operation can be performed by bypassing the
UI.** That is a claim about the DATA LAYER (Firestore rules), not about how many
screens have been rewritten. This document (a) maps every one of the
101 client-only screens to a priority tier using the phase brief's own
keyword lists, and (b) reports, for each P0 item, whether the underlying DATA is
now actually server-enforced — the thing that really matters — separately from
whether the SCREEN itself has been migrated onto that enforced data path yet.

## What this phase actually fixed at the data layer (not just documented)

Phase 34's static analysis of the real `firestore.rules` file found 8 collections
with an unscoped `create` rule (any authenticated user, no ownership check). This
phase fixed the 2 highest-confidence ones directly in `firestore.rules`:

- **`payments`** — `create` now requires `request.resource.data.createdBy ==
  request.auth.uid` (or Admin) — closes the ability for a non-admin session to
  fabricate a payment record self-claiming a DIFFERENT user as its creator. This
  is safe because the real write path (`src/services/commercialWorkflow.ts`)
  always sets `createdBy: actor.userId`, which is always the real Firebase Auth
  uid for a real session — verified by reading the actual write-path code, not
  guessed.
- **`qc_inspections`** — `create` now requires `isTechnician()` (admin + technician
  + qc_inspector), closing the ability for a `customer`/`supplier` session to
  create a QC record at all. Deliberately NOT a strict `inspectorId ==
  request.auth.uid` self-match — the real QC-assignment flow
  (`QcInspectorAssignmentScreen` -> `requestQC()`) lets one technician/admin
  assign a DIFFERENT technician as the inspector, which a strict self-match would
  have broken with no way to verify against a live emulator in this sandbox.

The remaining 6 static findings from Phase 34 (`workflow_instances`,
`workflow_executions`, `snags`, `notifications`, `delivery_receipts`, `documents`)
were deliberately NOT changed this phase — each either has no per-user field in
its domain model to scope against at all (`WorkflowInstance`/`WorkflowExecution`
  have no `createdBy`/`triggeredBy` field), or the real write path legitimately
creates a record ON BEHALF OF a different subject than the acting user (`Snag`'s
`assignedTo` is set by whoever triggers the QC_FAILED handler, not necessarily the
assignee). Tightening these blind, with no live emulator to verify against, risks a
real functional regression this pack's own rule #14 ("keep the application
buildable") and general engineering judgment argue against — flagged here as real,
open, prioritized follow-up work instead of guessed at.

## What "server authorization status" means for a P0 screen, precisely

A P0 screen in the table above falls into exactly one of two real states:

1. **Entity has a real Firestore rule already** (e.g. Payment, PurchaseOrder,
   User) — the DATA is protected server-side regardless of which screen writes
   it; a malicious direct Firestore call is already denied. The screen's own
   `DbManager` read/render path is real remaining work (dual-write bridge, then
   full cutover — Phase 15-18's proven pattern), but it is NOT a security hole —
   it is a data-consistency/UX modernization item.
2. **No Firestore collection/rule exists for this entity yet** — this IS a real
   security gap: nothing stops a direct Firestore write, because there is nothing
   to write to yet. Closing this needs Phase 02-04-shaped work (domain model +
   repository + rules) before a screen migration is even possible — scoped,
   named, real follow-up work, not silently glossed over.
