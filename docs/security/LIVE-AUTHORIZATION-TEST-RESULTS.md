## Part 2 — Static analysis of the REAL `firestore.rules` file (not a live test, clearly distinct from Part 1)

This IS something this sandbox can do for real without a live credential:
directly read and analyze the actual deployed rules file for every
collection's `create`/`update` rule, checking whether it is scoped to the
acting user (a role gate like `isAdmin()`, or an ownership condition) or
accepts ANY authenticated user unconditionally (`allow create: if
isAuthenticated();` alone — no check that the new document belongs to, or
is created by, the person creating it).

**30 collection rule blocks examined.**

### Real findings — unscoped `create`, not documented as intentional

| Collection | Rule | Why this matters |
|---|---|---|
| `payments` | `allow create: if isAuthenticated();` | **P0 — financial.** ANY authenticated user (including a `customer` or `supplier` session) can create a Payment document for ANY project with an arbitrary amount and `createdBy` value — nothing ties it to a project they actually own. The read side IS scoped (`isRecordOwner('createdBy')`), but create is not. |
| `workflow_instances` | `allow create, update: if isAuthenticated();` | ANY authenticated user can create OR MODIFY a workflow instance record — no role or ownership gate on either operation. |
| `workflow_executions` | `allow create: if isAuthenticated();` | ANY authenticated user can write an execution-attempt record into what is meant to be an automation audit trail. |
| `qc_inspections` | `allow create: if isAuthenticated();` | ANY authenticated user, including a `customer`, can create a QC inspection record — a quality-gate-integrity concern, since `Handover.qcPassed` (the Phase 09 hard gate) derives from this collection's data via the event bus. |
| `snags` | `allow create: if isAuthenticated();` | ANY authenticated user can create a Snag (rework-trigger) record for any project. |
| `notifications` | `allow create: if isAuthenticated();` | ANY authenticated user can create a notification addressed to any `audienceUserId` — a spoofing/spam vector. |
| `delivery_receipts` | `allow create: if isAuthenticated();` | ANY authenticated user can create a delivery-receipt record unrelated to a shipment they actually received. |
| `documents` | `allow create: if isAuthenticated();` | ANY authenticated user can attach document metadata to any project. |

### Intentional-by-design exceptions (verified against the rules file's own comments — not findings)

| Collection | Why unscoped create is intended |
|---|---|
| `idempotency_keys` | A dedup registration record, not sensitive business data; the rules file's own comment says "any authenticated write path may register a dedup record." |
| `audit_logs` | The rules file's own comment: "Application server/client logs audit trail" — immutable once written, read is admin-only. |
| `observability_events` | The rules file's own comment: "a crashed session still needs to be able to report the crash" — immutable once written, read is admin-only. |
| `breakdown_sos` | A customer reporting an emergency for their own site is the intended broad-access UX; read is scoped to the reporter/assigned technician/admin. |
